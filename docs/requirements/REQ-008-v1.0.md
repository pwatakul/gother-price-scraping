# REQ-008: Standardized Booking-Window & Device Cross-Tracking
_Version: 1.0_

## Raw Requirement (plain language)
> I need the system to track the +1, +3, +7, +14, +30 booking windows. The hotel detail page must show the result of all that tracking. And I need cross-tracking between mobile and desktop — for example, +1 day with 1 night 2 adults on mobile **and** +1 day with 1 night 2 adults on desktop. It must be mandatory. The data must be the same standard so I can analyse it easily.

## Goal
Every scheduled scrape produces the **same fixed grid** of observations for every hotel group, so that prices are directly comparable across hotels, across days, and across devices without post-hoc normalization.

The grid is **5 booking windows × 2 devices = 10 scrape jobs per scheduler fire**, all at identical stay parameters:

| Dimension | Standard values |
|-----------|-----------------|
| Booking window (days before check-in) | `+1, +3, +7, +14, +30` |
| Device | `desktop`, `mobile_web` |
| Length of stay | 1 night |
| Rooms | 1 |
| Adults | 2 |

These values are **system constants, not per-config settings**. See [[ADR-006-booking-window-device-standard]] for why.

### Why this is not already satisfied by [[REQ-002-v1.1]]
- REQ-002 F-006 fires one job per entry of the free-form `scheduled_scrape_configs.lookahead_days` array. Two configs can legitimately hold different offsets, so coverage is ragged and cross-hotel comparison is unsound.
- `device` exists on `scrape_jobs` and `scrape_results` (migration `009`) but is **never written to `hotel_price_history`**. Since `hotel_price_history` is what backs the hotel detail page, the trend API and every materialized view, the device dimension is invisible to all analytics. The scheduler additionally hardcodes `device: Default::default()` (desktop), so `mobile_web` is never produced by automation at all.

## Scope notes
- `lookahead_days`, `los_variants`, `rooms` and `adults` were **dropped from `scheduled_scrape_configs`** in migration `019`. Once the scheduler stopped reading them, leaving them in place meant the API still *required* `lookahead_days` and the UI still collected values that were silently ignored — a worse outcome than removing them. A schedule now configures only *when* (`cron_expression`), *how* (`method`) and *whether* (`is_active`) to scrape; never *what*.
- On-demand scrape jobs created via the HTTP API are unaffected — they keep their free-form parameters. Only the *scheduled* path is standardized, so ad-hoc investigation of any window/device/LOS combination is still possible without polluting the standardized series.
- A manual run (F-010) is **additive** to the schedule: `fire_grid` does not touch `last_run_at`/`next_run_at`, so pressing "Run now" never delays the next cron fire. It also runs regardless of `is_active` — pausing stops the cron, but an explicit request is still an explicit request.

## Open Risks
| Risk | Detail |
|------|--------|
| **Device may not actually change the result** | [[REQ-001-v1.3]] already flags that neither SerpAPI nor the Gother API documents a parameter for varying results by device or login state. This requirement makes the device dimension *capturable, queryable and analysable*; it does **not** establish that mobile and desktop will return different prices. Until an upstream device parameter is confirmed, expect the two series to be identical, and read the `device` column as a recorded label rather than proof of a real price difference. |
| **10× job volume per fire** | Where a config previously fired 1–3 jobs it now fires 10, and each job scrapes every hotel in the group. The 10 jobs are *queued* through RabbitMQ and consumed by the worker at its own pace rather than run in parallel, so the burst is buffered rather than concurrent — no throttling was added. Watch scraper quota and rate limits as the number of active configs grows; that is the point at which a per-fire cap or stagger becomes worth building. |
| **Materialized view rebuild** | `mv_hotel_booking_window` must be dropped and recreated to add `device` to its grouping key. It is repopulated from `hotel_price_history` on the next refresh, so no history is lost, but the view is briefly empty during migration. |
| **Pre-existing rows default to `desktop`** | Rows written before migration `017` are backfilled with `device = 'desktop'`, which is accurate (the scheduler only ever produced desktop jobs) but is an assumption worth remembering when reading old data. |
