## Raw Requirement (plain language)
Same as v1.1, with the CEO brief's concrete scope now attached: scrape prices for a fixed list of 2200 Gother hotels (1200 Thailand/domestic, 1000 international) weekly, across a defined set of booking-window lead times per segment, for 1 night / 2 adults, from Gother plus 3 competing sources, across both desktop and mobile web, from a Thai IP, in both logged-out and logged-in (member) states — and show Gother's PO/BD team where Gother wins or loses on price, with every rate traceable to its source (URL + WHO ID for Gother rates).

## Goal
Unchanged from v1.1.

## Collection Data Scope (new in v1.2)
Source: `docs/raw/Req price scrapping - 17 July 26.xlsx`, sheet "Req Price Scrapping Hotels".

| Dimension | Domestic | International |
|-----------|----------|----------------|
| Hotel count | 1200 | 1000 (2200 total) |
| Booking window (days before check-in) | 0 (same-day), +1, +3, +7, +14, +30 | +7, +14, +30, +60, +90 |
| Length of stay / guests | 1 night, 2 adults | 1 night, 2 adults |
| Providers | Gother, Agoda, Trip, Wink | Gother, Agoda, Trip |
| Device | Desktop, Mobile Web | Desktop, Mobile Web |
| IP origin | Thai | Thai |
| Login state | Public and Member | Public and Member |
| Frequency | Weekly | Weekly |
| Price basis | Inclusive of tax and fee only | Inclusive of tax and fee only |

Additional rules from the brief:
- Display the **WHO ID** for every rate shopped through Gother.
- For direct-contract hotels (via Wink or HyperGuest), rates must be included in the rate shop and comparable with rates shown on the Gother website.
- If no rate is available for a specific check-in date/provider combination, **leave the field blank** (do not show zero or an error value).

## Acceptance Criteria
Carried forward from v1.1 (see [[REQ-001-v1.1]]), plus:
- [ ] Scrape coverage reaches 2200 hotels (1200 domestic / 1000 international) at the specified booking-window lead times per segment
- [ ] Agoda, Trip, and (domestic-only) Wink are scraped as named sources alongside Gother — not only via a generic aggregator
- [ ] Results are captured per device (Desktop, Mobile Web) and per login state (Public, Member)
- [ ] Every Gother-sourced rate displays its WHO ID
- [ ] Direct-contract (Wink/HyperGuest) rates appear in the comparison and are matched for apples-to-apples comparison
- [ ] Missing rates render as blank, not zero or an error state
- [ ] Weekly scheduled run covers the full 2200-hotel list

## Open Questions
- [ ] **Hotel-list format mismatch**: the brief's real hotel list (`docs/data/hotel-list-2200.csv`) uses columns `No, HID, Hotel-Name, UPDATE URL, SLUG, Supplier-or-Direct, Country, SEARCH` — this does not match F-002's spec (`hotel_name, city, country, checkin_date, checkout_date, rooms, adults, currency`). Should F-002 be extended to accept both formats, or should the import path be redesigned around HID/SLUG as the primary keys? **Needs design decision before implementation.**
- [ ] **Output schema gap**: the brief's example output (`docs/data/example-raw-data-schema.md`) has fields with no home in `hotel_price_history` (`task_id`, `Scrapping Round`, split tax-exclusive/inclusive price pairs, structured `Notes` codes). Does `hotel_price_history` need new columns, or is this an export-time transformation? **Needs an ADR before any schema migration.**
- [ ] **Provider-specific scraping (F-022)**: current architecture scrapes via SerpAPI as a Google Hotels aggregator ([[ADR-001-scraper-choice]]). The brief calls for named per-provider results (Agoda, Trip, Wink). Does SerpAPI's aggregated results reliably attribute to these exact providers, or are dedicated per-OTA scrapers needed? **Needs investigation + possible new ADR.**
- [ ] What does `Scrapping Round` (0/1 observed in the example data) represent — a retry counter, a batch identifier, something else? Not defined in the brief.
