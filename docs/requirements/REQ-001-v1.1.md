# REQ-001: Hotel Price Scraping — Core Module
_Version: 1.1 | Supersedes [[REQ-001-v1.0]]_

## What changed from v1.0
| Change | Reason |
|--------|--------|
| Repositioned as the "Hotel Module" of a larger multi-product platform | CEO vision: Hotels → Experiences → Flights |
| Price history persistence added as a hard requirement (was out of scope) | Analytics and market intelligence cannot work without historical data |
| Scheduled/automated scraping added as dependency | Manual-only scraping cannot build the data volume needed for analytics |
| Explicit product_type field on all scrape data | Enables shared infrastructure across hotel, experience, and flight products |
| Forward references to REQ-002, REQ-003, REQ-004, REQ-005 added | These REQs depend on the hotel module being the foundation |

## Context: Where this fits in the platform
This REQ covers the **hotel price scraping module only**. The system is designed to grow:

```
Phase 1 (now)   → Hotel price comparison (this REQ)
Phase 2 (next)  → Experience/Activity price comparison (REQ-004)
Phase 3 (later) → Flight price comparison (REQ-004)
```

All phases share: job queue, price history store, analytics layer, and the market intelligence dashboard.

## Raw Requirement (plain language)
Users (Product Owner, Business Development) can define a list of hotels, trigger price lookups across competing OTAs, and see a side-by-side price comparison against Gother's prices. All prices are stored historically so that trends and market positioning can be tracked over time. The system scrapes automatically on a schedule — not just when a user manually requests it.

## Goal
Give Gother's PO and BD team always-up-to-date market intelligence on hotel pricing. Know at any moment whether Gother is winning or losing on price, for which hotels, and by how much — across time.

## Acceptance Criteria
- [x] User can create hotel groups and import hotels via Excel
- [x] User can trigger an on-demand scrape job with date range and guest params
- [x] Scrape fetches prices from SerpAPI (Google Hotels aggregator) and Gother API
- [x] All prices normalized to THB; room types and meal plans normalized to standard labels
- [x] Job progress trackable in real time (per-hotel status)
- [x] Results exportable as Excel
- [ ] Excel import accepts per-row checkin_date, checkout_date, rooms, adults, currency (blank → job-level defaults)
- [ ] Scrape job supports `los_variants[]` — scrapes the same hotel at multiple lengths of stay (1N, 2N, 3N, 5N, 7N) to capture LOS-based OTA discounts
- [ ] Results include source_url + scraped_at evidence per price entry
- [ ] ⚠️ badge shown when room type on OTA differs from Gother's room type (apple-to-apple warning)
- [ ] ChatGPT scraper (Method 1) produces prices merged into the same comparison table
- [ ] Every scraped price is written to `hotel_price_history` table (time-series, persistent)
- [ ] Scheduled scrape configs can be created per hotel group (cron-based)
- [ ] System scrapes automatically at configured intervals without manual trigger
- [ ] Price history queryable by hotel + date range + source via API

## Out of Scope (v1.1)
- User authentication (no auth yet)
- Direct browser scraping (API-only)
- WebSocket push (polling-based progress)
- Analytics charts and dashboards → see [[REQ-003-v1.0]]
- Multi-product (experience/flight) → see [[REQ-004-v1.0]]
- Explicit hotel availability tracking — **availability is implicit**: if a price is returned for a date, rooms are available; if no price, the hotel is sold out or unavailable for those dates. No separate availability call or table needed for hotels.

## Dependencies
- SerpAPI key (Google Hotels engine)
- Gother internal API credentials
- PostgreSQL, Redis, RabbitMQ (Docker Compose)
- [[REQ-002-v1.0]] — price history storage must be designed before F-015/F-016/F-017 are implemented
- [[data-model-v1.1]] — updated schema with price_history and scheduled_scrape_configs tables

## Open Questions
- [x] What lookahead window should automated scraping use? → Resolved: `lookahead_days` is a configurable array per `scheduled_scrape_config` (e.g., `[7, 14, 30, 60]`) — see [[REQ-002-v1.0]]
- [x] Should scheduled scraping cover all date combinations or a fixed set of lead times? → Resolved: fixed set of lead-time days configured per schedule — see [[REQ-002-v1.0]]
- [x] Is there a TripAdvisor API to integrate directly as an additional OTA source? → Resolved: **No** — TripAdvisor direct integration is out of scope for Phase 1. ChatGPT (Method 1) queries TripAdvisor internally as part of its own lookup — we do not call TripAdvisor's API separately.
