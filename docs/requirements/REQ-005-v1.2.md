# REQ-005: Data Platform & Scalability
_Version: 1.2 | Supersedes [[REQ-005-v1.1]]_

## What changed from v1.1
| Change | Reason |
|--------|--------|
| F-002 (auto-create next month's partition) now Done | Closed the gap v1.1 flagged — see below |

F-002 is implemented at the application level, not via `pg_partman` (still deliberately not added as a dependency, consistent with v1.0/v1.1's reasoning): `PriceHistoryRepo::ensure_future_partitions()` (`backend/src/db/repositories/price_history_repo.rs`) issues an idempotent `CREATE TABLE IF NOT EXISTS <name> PARTITION OF hotel_price_history FOR VALUES FROM ($1) TO ($2)` per month in a rolling 4-month window, built from a pure `partition_ranges()` helper (unit tested, including a December→January year-rollover case). A new background loop, `backend/src/worker/partition_manager.rs`, calls this once at process startup and then once every 24 hours (`tokio::time::interval`), spawned in `main.rs` alongside the existing worker/scheduler loops. A month is never at risk of missing its partition as long as the process has been running at any point in the preceding ~4 months before that month starts.
