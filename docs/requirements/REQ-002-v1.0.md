# REQ-002: Price History & Automated Scraping
_Version: 1.0_

## Raw Requirement (plain language)
Every price that the system ever scrapes must be stored permanently in a time-series table, independent of individual scrape jobs. The system must also be able to scrape on a schedule (daily, weekly) without requiring a human to trigger it. This historical data is the foundation for all analytics, trend graphs, and market intelligence features.

## Goal
Build up a continuously growing dataset of hotel (and future: experience/flight) prices across all OTA sources over time. This "price database" is what allows PO and BD to answer questions like: "Is Agoda getting cheaper this month?", "How often does Gother have the best price?", "What's the price trend for hotel X over the past 90 days?"

## Acceptance Criteria
- [ ] Every price scraped (on-demand or scheduled) is written to `hotel_price_history` table
- [ ] `hotel_price_history` is partitioned by month (`scraped_at`) for performance at scale
- [ ] Scheduled scrape configs can be created, activated, and deactivated via API
- [ ] Scheduler automatically triggers scrape jobs at the configured cron interval
- [ ] Scheduler uses configurable lookahead windows (e.g., scrape prices for 30/60/90 days out)
- [ ] Existing on-demand scrape jobs also write to price_history (dual-write)
- [ ] Price history queryable via API: filter by hotel_id, source, checkin_date range, scraped_at range
- [ ] Data retention policy configurable (default: keep all data, min 2 years)
- [ ] System handles duplicate prevention (same hotel + source + checkin + scraped_at window)

## Functional Requirements
| ID | Description | Priority |
|----|-------------|----------|
| F-001 | Dual-write: all scrape results written to both `scrape_results` (job-bound) and `hotel_price_history` (persistent) | High |
| F-002 | `hotel_price_history` stores: hotel_id (FK → hotels), source, room_type, price_thb, original_price, currency, exchange_rate_id (FK → currency_exchange_rates), meal_plan, cancellation, source_url, checkin_date, checkout_date, rooms, adults, scrape_job_id (nullable FK), scraped_at | High |
| F-003 | Create scheduled scrape config: hotel_group_id, cron_expression, lookahead_days[], los_variants[], rooms, adults, is_active — `los_variants` defaults to `[1]` (single night); set `[1, 2, 3, 5, 7]` to scrape multiple lengths of stay per run | High |
| F-004 | List / update / delete scheduled scrape configs via API | High |
| F-005 | Cron worker (background process) reads active configs and fires scrape jobs automatically | High |
| F-006 | Lookahead scraping: for each scheduled run, create jobs for each configured lookahead window (e.g., checkin = today+30, today+60, today+90) | High |
| F-007 | API: `GET /price-history` — query price history with filters (hotel_id, source, checkin_date range, scraped_at range, limit/offset) | High |
| F-008 | API: `GET /price-history/hotel/:id/trend` — aggregated price trend over time for one hotel | High |
| F-009 | Idempotency: scheduler must not create duplicate jobs for the same config + date window within the same day | Medium |
| F-010 | Data retention: configurable RETENTION_DAYS env var; cleanup job removes records older than limit | Medium |
| F-011 | Admin API: trigger cleanup job manually | Low |

## Non-Functional Requirements
| ID | Description |
|----|-------------|
| NF-001 | Scalability: `price_history` partitioned by `scraped_at` month (PostgreSQL RANGE partitioning). New partitions created automatically |
| NF-002 | Volume estimate: 100 hotels × 10 sources × 3 lookaheads × 365 days ≈ 1.1M rows/year — must stay performant |
| NF-003 | Indexes: (hotel_id, checkin_date, scraped_at) and (source, scraped_at) for common query patterns |
| NF-004 | Cron worker should be fault-tolerant: failure of one scheduled run must not block future runs |
| NF-005 | Dual-write must not slow down the existing on-demand scrape path — write price_history async or in same DB transaction |

## Out of Scope (v1.0)
- Real-time streaming pipeline (Kafka/Flink) — standard PostgreSQL is sufficient for current scale
- Multi-region data replication
- Custom retention per hotel group (global config only)
- Analytics charts — see [[REQ-003-v1.0]]

## Open Questions
- [x] What cron intervals make sense as defaults? → Resolved: **No system-wide default** — cron expression is fully configurable per `scheduled_scrape_config` by the user (e.g., weekly, monthly, or any custom schedule). The `cron_expression` field on `scheduled_scrape_configs` accepts any standard 5-field cron string.
- [x] Should we keep ALL history forever, or define a rolling window? → Resolved: **Keep forever** — price history is a strategic data asset for future big data and analytics. No retention cleanup. `RETENTION_DAYS` env var defaults to `0` (disabled).
- [x] Lookahead windows: per-config or system-wide fixed? → Resolved: per-config `lookahead_days[]` array (e.g., `[30, 60, 90]`) — see F-003
- [x] Keep both records if scraped twice in one day, or deduplicate? → Resolved: append-only, keep both — queries filter by `scraped_at` range as needed — see F-009
