# REQ-008: Standardized Booking-Window Tracking
_Version: 1.1 | Supersedes [[REQ-008-v1.0]]_

## What changed from v1.0
| Change | Reason |
|--------|--------|
| Device cross-tracking dropped — the grid is 5 booking windows, not 5 × 2 devices | v1.0's own Open Risk ("device may not actually change the result") was tested and confirmed. SerpAPI's `google_hotels` engine documents no `device` parameter and silently ignores one; desktop vs mobile across 3 hotels and **69 common sources produced zero price differences**. The grid was writing two identical copies of every row, and the hotel page's mobile-vs-desktop comparison could only ever display zero — presenting a measured finding where none exists. See [[ADR-010-drop-device-and-member-dimensions]] |
| Login state fixed to `public` | No API parameter exists for logged-in or member rates, and we hold no credentials for the target sites. Member pricing is unobservable, not merely unimplemented |
| Jobs per fire: 10 → **5** | Direct consequence of the above. Also halves cost: the grid was 200 SerpAPI searches per fire at 20 hotels, against a ~250/month free tier |
| Device and login-state **columns retained** | Unlike the config columns dropped in migration `019`, these are written on every row and are accurate. They record what an observation was captured under, and a future direct-OTA or Gother scraper could genuinely vary by device |

## Raw Requirement (plain language)
> I need the system to track the +1, +3, +7, +14, +30 booking windows. The hotel detail page must show the result of all that tracking. The data must be the same standard so I can analyse it easily.
>
> _(v1.1: the original request also asked for mandatory mobile/desktop cross-tracking. Stakeholder confirmed focusing on public + desktop once it was shown the two are identical and member rates are unreachable without login.)_

## Goal
Every scheduled scrape produces the **same fixed grid** of observations for every hotel group, so prices are directly comparable across hotels and across days without post-hoc normalization.

The grid is **5 booking windows = 5 scrape jobs per scheduler fire**, all at identical parameters:

| Dimension | Standard value |
|-----------|----------------|
| Booking window (days before check-in) | `+1, +3, +7, +14, +30` |
| Device | `desktop` (recorded, never varied) |
| Login state | `public` (recorded, never varied) |
| Length of stay | 1 night |
| Rooms | 1 |
| Adults | 2 |

These are **system constants, not per-config settings** — see [[ADR-006-booking-window-device-standard]] for why comparability requires that.

## Scope notes
- `lookahead_days`, `los_variants`, `rooms` and `adults` were dropped from `scheduled_scrape_configs` in migration `019`. A schedule configures only *when* (`cron_expression`), *how* (`method`) and *whether* (`is_active`) to scrape; never *what*.
- On-demand jobs via the HTTP API keep their free-form parameters — ad-hoc investigation stays possible without polluting the standardized series. The API still accepts `device`/`login_state`; the UI simply always sends `desktop`/`public`.
- A manual run is **additive**: `fire_grid` does not touch `last_run_at`/`next_run_at`, so "Run now" never delays the next cron fire.

## Open Risks
| Risk | Detail |
|------|--------|
| **SerpAPI quota** | A full grid run is 5 windows × 20 hotels = **100 searches**. The free tier is ~250/month, so daily scheduling (~3,000/month) needs the paid Developer plan. Cadence should be a deliberate decision before enabling a schedule. |
| **Device conclusion is source-specific** | ADR-010 establishes that *SerpAPI's Google Hotels aggregation* does not vary by device — not that OTAs never do. A direct Agoda/Trip.com scraper could well see app- or mobile-only rates. If that becomes a goal, revisit ADR-010 rather than citing it as proof device never matters. |
| **Member pricing is out of scope indefinitely** | Not merely unimplemented — unobservable without credentials. Any analysis assuming member rates are covered would be wrong. |
| **Pre-existing rows default to `desktop`** | Rows written before migration `017` are backfilled with `device = 'desktop'`, which is accurate but worth remembering when reading old data. |

## Verification
Confirmed:
1. `cargo test` — 47/47 pass, including `grid_is_one_job_per_standard_booking_window`, which asserts exactly 5 distinct windows with no device axis.
2. `npx tsc --noEmit` — frontend type-checks clean.
3. Live scrape over the 20 seeded Thai hotels: **18/20 succeeded**, 112 rows across 8 providers. The 2 failures (Mandarin Oriental, Amanpuri) report `serpapi: failed (No prices found)` — SerpAPI genuinely returned no prices for those on that date, not a system fault.
4. Hotel detail page renders the 5-row coverage table with no Device column.

Not re-verified live: a scheduled "Run now" firing 5 jobs. The grid expansion is asserted by unit test, and a live run would consume ~100 SerpAPI searches against a nearly-exhausted free tier — deliberately deferred rather than skipped silently.
