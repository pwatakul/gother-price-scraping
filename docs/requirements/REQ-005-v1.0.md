# REQ-005: Data Platform & Scalability
_Version: 1.0_

## Raw Requirement (plain language)
The system must be designed from the start to handle growing data volumes as more hotels, more product types, and more OTA sources are added over months and years. Price history is the core asset — it must be queryable fast, stored efficiently, and exportable for external BI tools. The system should be simple enough that a small team can maintain it, but structured so that adding analytics or a data science layer later is straightforward.

## Goal
Design the data storage and query layer so that the system remains fast and maintainable at 10x current scale — without needing a rewrite. Make the raw price data accessible enough that a future data analyst or BI tool can plug in and query it directly.

## Scale Targets
| Metric | Year 1 Estimate | Year 3 Estimate |
|--------|----------------|----------------|
| Hotels tracked | 100 | 500 |
| OTA sources | 5 | 10 |
| Lookahead windows | 3 | 5 |
| Scrape frequency | Daily | Daily + on-demand |
| Rows/year in hotel_price_history | ~1.1M | ~9M |
| Total rows (3 years) | ~3M | ~27M |
| Query response target | < 2s | < 3s |

> [!NOTE]
> At these volumes, standard PostgreSQL with proper partitioning and indexes is sufficient. No need for a data warehouse (BigQuery, Snowflake) in the near term.

## Acceptance Criteria
- [ ] `hotel_price_history` table uses PostgreSQL RANGE partitioning by `scraped_at` (monthly partitions)
- [ ] New monthly partitions created automatically (via pg_partman or migration script)
- [ ] Core analytics queries use materialized views; views refreshed after each scheduled scrape run
- [ ] Data export API: download raw `hotel_price_history` as CSV/JSON with filters
- [ ] Read replica supported (app can route analytics queries to replica)
- [ ] RETENTION_DAYS configurable env var; cleanup job removes old partitions (DROP PARTITION, not row-by-row DELETE)
- [ ] All indexes documented and justified in [[data-model-v1.1]]

## Functional Requirements
| ID | Description | Priority |
|----|-------------|----------|
| F-001 | `hotel_price_history` partitioned by `scraped_at` month using PostgreSQL RANGE partitioning | High |
| F-002 | Partition management: auto-create next month's partition at start of each month | High |
| F-003 | Materialized view: `mv_market_position` — latest price per hotel per source (for dashboard load) | High |
| F-004 | Materialized view: `mv_daily_avg_price` — daily average price per hotel per source (for trend charts) | High |
| F-005 | Materialized view refresh triggered after each scheduled scrape run completes | High |
| F-006 | Data export API: `GET /export/price-history` with filters: hotel_id, source, checkin_date range, scraped_at range, format (csv/json) | Medium |
| F-007 | Read replica routing: analytics endpoints optionally use DATABASE_REPLICA_URL if configured | Medium |
| F-008 | Retention cleanup: cron job drops `hotel_price_history` partitions older than RETENTION_DAYS | Medium |
| F-009 | Index strategy: composite indexes on (hotel_id, checkin_date, scraped_at) and (source, scraped_at, price_thb) — see [[data-model-v1.1]] for full index definitions | High |
| F-010 | Schema documentation: every index in [[data-model-v1.1]] has a comment explaining its query pattern | Low |

## Non-Functional Requirements
| ID | Description |
|----|-------------|
| NF-001 | Query performance: `mv_market_position` queries must return in < 500ms for up to 500 hotels |
| NF-002 | Partition drop (retention cleanup) must not lock the main table |
| NF-003 | Backup strategy: daily pg_dump retained for 30 days minimum |
| NF-004 | No ORM for analytics queries — raw SQL with sqlx for control over query plan |
| NF-005 | Simplicity: no separate OLAP/data warehouse in v1 — PostgreSQL handles everything |

## Materialized Views Plan
| View | Source | Refresh | Used by |
|------|--------|---------|---------|
| `mv_hotel_market_position` | hotel_price_history | After each scrape run | Dashboard market position table |
| `mv_hotel_daily_avg_price` | hotel_price_history | Daily | Price trend charts |
| `mv_hotel_win_rate` | hotel_price_history | Daily | Win rate metric per hotel |
| `mv_hotel_competitor_summary` | hotel_price_history | After each scrape run | Competitor heatmap |
| `mv_hotel_booking_window` | hotel_price_history | After each scrape run | Booking window chart — avg price by days_in_advance per (hotel, source) |
| `mv_hotel_parity_violations` | hotel_price_history | After each scrape run | Rate parity alert — hotels where Gother exceeds best OTA by > threshold |

## Future Considerations (not in scope for v1)
- **Kafka / event streaming**: if scrape volume exceeds ~10k events/hour, consider streaming price events to a topic that feeds price_history asynchronously
- **ClickHouse / columnar store**: if analytical queries slow down at 100M+ rows, migrate `hotel_price_history` to a columnar store while keeping PostgreSQL for transactional data
- **dbt**: if the number of materialized views grows beyond 10, use dbt for view dependency management and documentation
- **Data Science / ML**: `hotel_price_history` is the training data for future forecasting models

## Out of Scope (v1.0)
- Kafka / streaming pipeline
- Data warehouse (BigQuery, Snowflake, Redshift)
- ML/forecasting models
- Multi-region replication
- Real-time data push to external systems

## Open Questions
- [x] Partition management: `pg_partman` or migration script? → Resolved: **`pg_partman`** — more robust, handles auto-creation of future partitions without manual intervention.
- [x] Read replica: required at launch or optional? → Resolved: **Optional** — configured via `DATABASE_REPLICA_URL` env var. Analytics endpoints use it when set; fall back to primary when not set.
- [x] Retention period? → Resolved: **Keep forever** — price history is a strategic big data asset. `RETENTION_DAYS` defaults to `0` (disabled). Partition DROP mechanism remains in the codebase but is not scheduled by default.
