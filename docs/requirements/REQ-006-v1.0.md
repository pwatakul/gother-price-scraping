# REQ-006: Price Forecasting & Predictive Analytics
_Version: 1.0_

> [!WARNING]
> This REQ is **Phase 4 — planned but not in scope until Phase 1–3 are stable and sufficient historical data has been accumulated** (minimum 6 months of `hotel_price_history`). The value of forecasting depends entirely on the depth of historical data.

## Raw Requirement (plain language)
After accumulating months of price history across hotels and OTA sources, the system should be able to predict how prices will move — for a given hotel, on a given check-in date, from a given OTA source. This enables PO and BD to act ahead of the market: book early when prices are predicted to rise, or wait when prices are predicted to fall.

## Goal
Transform historical price data from a backward-looking record into a forward-looking intelligence tool. Answer:
1. **Will this hotel get cheaper or more expensive next week?**
2. **At what point in the booking window is Agoda typically cheapest?**
3. **Is there a seasonal price pattern we can exploit for procurement / partner negotiation?**

## Target Users
| User | Need |
|------|------|
| Product Owner | Know when to feature-flag promotional rates before competitors drop prices |
| Business Development | Predict market opportunity windows for partner negotiation |
| Data Analyst | Build and validate forecasting models on clean historical data |

## Acceptance Criteria
- [ ] System predicts price_thb for a given (hotel_id, source, checkin_date) up to 90 days ahead
- [ ] Confidence interval shown alongside each prediction (e.g., ฿4,200 ± ฿300)
- [ ] Seasonal patterns identified automatically (e.g., high season uplift %, weekend premium)
- [ ] Booking window recommendation: "Book now / Wait" signal per hotel based on predicted price curve
- [ ] Forecast accuracy tracked: MAPE (Mean Absolute Percentage Error) shown per hotel per source
- [ ] Minimum 6 months of `hotel_price_history` required before forecasting is enabled for a hotel

## Functional Requirements
| ID | Description | Priority |
|----|-------------|----------|
| F-001 | **Forecast model training pipeline** — scheduled job (weekly) retrains model per (hotel, source) using all available `hotel_price_history` | High |
| F-002 | **Forecast API** — `GET /forecast/:hotel_id` returns predicted price_thb + confidence interval per source per date, up to 90 days ahead | High |
| F-003 | **Price forecast chart** — extend existing trend chart in analytics dashboard with a dashed forecast line beyond today | High |
| F-004 | **"Book Now / Wait" signal** — binary recommendation per hotel per OTA: if predicted price is trending up, signal "Book Now"; if trending down, "Wait" | Medium |
| F-005 | **Seasonal pattern detection** — identify recurring price uplift patterns (e.g., +18% in December, +12% on Fridays) per hotel per source | Medium |
| F-006 | **Booking window recommendation** — for each hotel, show at which `days_in_advance` bucket prices are historically cheapest (derived from `mv_hotel_booking_window`) | Medium |
| F-007 | **Forecast accuracy dashboard** — MAPE per hotel per source, updated after each model training run | Low |
| F-008 | **Data sufficiency gate** — disable forecasting for a hotel until it has ≥ 180 days of `hotel_price_history`; show "Insufficient data" state in UI | High |
| F-009 | **Forecast export** — include forecast data in Excel analytics export | Low |

## Non-Functional Requirements
| ID | Description |
|----|-------------|
| NF-001 | Model training must run as a background job — must not block the API or real-time scraping |
| NF-002 | Forecast models stored per (hotel_id, source) — one model per combination |
| NF-003 | Minimum viable approach: time-series regression (linear trend + seasonal decomposition); upgrade to Prophet or ARIMA when data volume justifies |
| NF-004 | Forecast generation must complete in < 5 seconds per hotel per source at query time (pre-computed, not on-demand) |
| NF-005 | Forecast results cached in Redis with 24-hour TTL; retrained weekly |

## Forecasting Approach (recommended progression)

| Stage | Method | When to use |
|-------|--------|-------------|
| **Stage 1** | Linear regression + seasonal dummy variables | 6–12 months of data; fast, interpretable |
| **Stage 2** | Facebook Prophet | 12+ months; handles holidays, seasonality automatically |
| **Stage 3** | ARIMA / SARIMA | 2+ years; strong seasonal patterns, stationary series |
| **Stage 4** | LSTM / deep learning | 3+ years, 10k+ rows per hotel; if Stage 1–3 MAPE > 10% |

Start with Stage 1. Move up only when MAPE on the validation set exceeds acceptable threshold (> 10% error).

## Data Requirements
- Minimum: 180 days of daily `hotel_price_history` per (hotel, source) combination
- Ideal: 365+ days (captures full seasonal cycle)
- Training/validation split: last 30 days held out for validation; rest for training
- Features: price_thb, checkin_date, days_in_advance, day_of_week, month, is_weekend, is_holiday_TH

## Out of Scope (v1.0)
- Real-time price prediction (predictions are pre-computed nightly)
- Demand forecasting (requires external data: search volumes, events)
- Revenue optimization / dynamic pricing recommendations (beyond our data)
- Flight and experience price forecasting (follow same pattern once hotel is stable)
