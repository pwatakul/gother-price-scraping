# REQ-004: Multi-Product Support (Experiences & Flights)
_Version: 1.0_

> [!WARNING]
> This REQ is **planned but not yet in scope**. Do not implement until hotels (REQ-001) and price history (REQ-002) are stable. The purpose of documenting it now is to ensure architectural decisions in the hotel module do not block this expansion.

## Raw Requirement (plain language)
Gother sells more than hotels. The same price intelligence platform should eventually cover experiences/activities (tours, tickets, local experiences) and possibly flights. Each product type has its own scraping sources and comparison fields, but should reuse the same job queue, price history store, and analytics layer as hotels. For experiences, availability (time slots and remaining capacity) is also a key piece of intelligence — not just price.

## Goal
Ensure the platform architecture is product-type-agnostic from day one, so adding a new product type (experience, flight) is a matter of adding a new scraper module — not redesigning the database or analytics layer.

## Acceptance Criteria (Phase 2 — Experiences)
- [ ] Experience items have their own entity: name, category, city, country, duration, provider
- [ ] Experience groups (same concept as hotel groups for batch processing)
- [ ] Scraper module for experiences pulls from: Klook (priority), Viator, GetYourGuide, Gother internal
- [ ] Price comparison fields adapted: activity_name, category, duration, included_items, price_thb
- [ ] `experience_price_history` table created (separate from `hotel_price_history`) with direct FK to `experiences`, shares `currency_exchange_rates` via `exchange_rate_id`
- [ ] `experience_availability` table tracks time-slot availability per experience per source per date
- [ ] Analytics dashboard supports switching between product types (hotel view / experience view)
- [ ] Excel import/export template adapted for experience fields

## Availability Strategy by Product Type

| Product | Approach | Reason |
|---------|----------|--------|
| **Hotel** | **Implicit** — if price is returned, rooms are available; no price = sold out | OTAs only return prices for available rooms; no separate availability call needed |
| **Experience** | **Explicit** — scrape time-slot availability separately via `experience_availability` table | Experiences have limited capacity per time slot (e.g., 9 AM / 2 PM tours); slots sell out independently of price |
| **Flight** | **Implicit** — if a fare is returned, seats are bookable; seat counts not exposed by public APIs | Airlines/GDS don't expose raw seat inventory via public scraping APIs |

### experience_availability schema (Phase 2)
| Field | Type | Description |
|-------|------|-------------|
| id | UUID | Primary key |
| experience_id | UUID | FK → experiences(id) |
| source | VARCHAR | `klook`, `viator`, `getyourguide`, `gother` |
| activity_date | DATE | Date of the activity |
| time_slot | TIME | Start time of the slot (nullable for all-day experiences) |
| slots_remaining | INTEGER | Capacity left (null = unknown, 0 = sold out) |
| is_available | BOOLEAN | Quick flag: is this slot bookable right now? |
| source_url | TEXT | Deep link to OTA listing for this slot |
| scraped_at | TIMESTAMPTZ | When this snapshot was taken — partition key |

## Non-Functional Requirements
| ID | Description |
|----|-------------|
| NF-001 | Adding a new product type is **additive only** — one new migration creates the new `<product>_price_history` table; no changes to existing tables, job queue, or analytics infrastructure |
| NF-002 | Scraper modules are pluggable — each product type maps to its own list of `Scraper` trait implementations |
| NF-003 | Shared infrastructure (RabbitMQ, Redis, PostgreSQL, `currency_exchange_rates`) handles all product types without modification |

## Architecture Principle

> Each product type gets its **own price history table** with a direct FK to its own entity table (`hotel_id`, `experience_id`, `route_id`). All history tables share `currency_exchange_rates` via `exchange_rate_id` for auditable currency conversion.
>
> There is **no shared polymorphic `price_history` table** and no `product_type + reference_id` pattern — this was evaluated and rejected in [[ADR-002-price-history-schema]] due to NULL columns, missing FK integrity, and poor query performance.
>
> Adding Experiences in Phase 2 = one new migration (`experience_price_history`) + new scraper modules. No changes to `hotel_price_history`, job queue schema, or analytics infrastructure.

## Out of Scope (this REQ)
- Flight scraping (Phase 3)
- Package deals (hotel + experience bundle)
- Real-time availability push / webhooks (polling-based availability snapshots only)
- Hotel availability tracking (implicit from price scraping — no separate call needed)
