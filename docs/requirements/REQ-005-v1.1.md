# REQ-005: Data Platform & Scalability
_Version: 1.1 | Supersedes [[REQ-005-v1.0]]_

## What changed from v1.0
| Change | Reason |
|--------|--------|
| F-001–F-005, F-009 implemented | Partitioned `hotel_price_history`, 5 of the 6 planned materialized views, refresh-after-every-job |
| `mv_hotel_competitor_summary` dropped from the plan | No SQL definition ever existed for it in any design doc; the competitor heatmap (REQ-003 F-004) is built directly from `mv_hotel_market_position` instead — no separate view needed |
| View refresh triggered after **every** scrape job (scheduled or on-demand), not just scheduled runs | Stricter than v1.0's NF-004 ("no real-time refresh required"), but costs nothing extra (same code path) and keeps a live demo from showing stale analytics after a manual test job |
| F-002 (auto-create next month's partition) not automated | No `pg_partman` dependency added — partitions for the current + next 3 months are created once at migration time (`014_create_hotel_price_history_partitions.sql`, computed dynamically from the migration run date, not hardcoded); creating further future partitions remains a manual follow-up migration, documented as a known gap rather than silently missing |
| F-006/F-007/F-008 (export API, read replica, retention cleanup) | F-006 done (`GET /export/price-history`, csv/json); F-007 (read replica routing) and F-008 (retention cleanup) deferred — no read replica exists yet, and retention already resolved to "keep forever" in v1.0 |
